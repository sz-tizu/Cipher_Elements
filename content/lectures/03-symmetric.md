## §1 PRF と PRP: 理想の部品を定義する

<div class="q" markdown="1">
同じ鍵で何度も暗号化するために、どんな性質を持つ「鍵付きの関数」が欲しいのか。
</div>

### 1.1 欲しいもの: ランダムな関数の巨大な表

理想を言えば、こんな関数が欲しいんです。入力（128 ビット）ごとに、出力（128 ビット）をサイコロで独立に決めた、巨大な表です。どの入力を問い合わせても、その答えは他の答えと無関係な乱数で、表を知らない人には予測できません。この表の値を鍵の列として使えば、入力を毎回変える限り、第2回のワンタイムパッドと同じ安全性が得られます。

ただし、この表は 2^128 行あり、保存できません。そこで、短い鍵 k から、この表と見分けがつかない関数 F_k を作ることを考えます。第2回の PRG が「列」を偽装したのに対し、今度は「表」を偽装するわけです。

<div class="box def" markdown="1">
**定義（疑似ランダム関数、PRF）** 鍵付きの関数 F_k が PRF であるとは、どんな PPT の識別器 D も、次の2つを無視できる差でしか見分けられないことをいう。

- 鍵 k をランダムに選んだ F_k に、好きな入力を問い合わせられる
- 本物のランダムな関数（巨大な表）に、好きな入力を問い合わせられる
</div>

PRG と違うのは、識別器が「好きな入力を選んで何度も問い合わせられる」点です。だから PRF の安全性は、IND-CPA の暗号化オラクルとよく噛み合います。

### 1.2 PRP: 逆算できる版

ブロック暗号は、暗号化したものを復号する必要があるので、出力から入力に戻せなければなりません。つまり「関数」ではなく「置換」（入力と出力が一対一に対応する並べ替え）です。

<div class="box def" markdown="1">
**定義（疑似ランダム置換、PRP）** 鍵付きの置換 E_k が PRP であるとは、どんな PPT の識別器も、E_k と本物のランダムな置換を、無視できる差でしか見分けられないことをいう。逆向き（復号）の問い合わせも許すものを、強い PRP と呼ぶ。
</div>

AES を使うときに信じている仮定は、「AES は（強い）PRP である」ということです。

### 1.3 PRF と PRP はどれくらい違うか

ランダムな関数とランダムな置換の違いは、たった1つです。関数は違う入力が同じ出力になる（重なる）ことがありますが、置換は決して重なりません。小さな例で比べてみてください。

<figure class="widget" data-widget="prf-table"></figure>

逆に言えば、重なりが見つかるまでは2つは区別できません。そして重なりが見つかるのは、第1回の誕生日の確率から、約 2^(n/2) 回の問い合わせのあとです。

<div class="box thm" markdown="1">
**PRF/PRP スイッチング補題** n ビットのランダムな置換とランダムな関数を、q 回の問い合わせで見分けられる確率は、高々 q(q−1)/2^(n+1) である。
</div>

この補題のおかげで、PRF を仮定して作った証明（たとえば CTR モード）を、PRP であるブロック暗号にそのまま使えます。誤差は q²/2^(n+1) だけです。

### 1.4 同じ鍵で暗号化してよい量

この誤差の項が、実務の重要な数字を決めます。ブロック長 n の暗号で q ブロックを暗号化すると、攻撃者は約 q²/2^(n+1) の確率で「ランダムな置換ではない」ことに気づけます。下の図でブロック長と量を変えてみてください。

<figure class="widget" data-widget="data-limit"></figure>

| 暗号 | ブロック長 | 問題になり始める量の目安 | 実際に起きたこと |
| --- | --- | --- | --- |
| DES、3DES、Blowfish | 64 ビット | 2^32 ブロック（32 GB） | Sweet32 攻撃（2016年）。HTTPS の長時間接続で 3DES の平文の一部を復元 |
| AES | 128 ビット | 2^64 ブロック（約 3 × 10^20 バイト） | 実用上は問題にならない。ただし運用モードごとの上限は別にある（第4回） |

AES のブロック長が 128 ビットに決まった理由の1つがこれです。

<div class="sum" markdown="1">
- PRF は「ランダムな関数の巨大な表」を、PRP は「ランダムな並べ替え」を、短い鍵で偽装したもの
- ブロック暗号は PRP として振る舞うことを期待されている
- PRF と PRP の差は「出力が重なるか」だけで、約 2^(n/2) 回の問い合わせまでは見分けられない
- その結果、ブロック長 n の暗号は、同じ鍵で約 2^(n/2) ブロックが上限になる
- では、ランダムに見えて、しかも逆算できる置換をどう作るのか。次の §2 で設計の原理を見る
</div>

## §2 ブロック暗号の作り方: 混乱と拡散

<div class="q" markdown="1">
「ランダムに見える」と「必ず逆算できる」を両立する置換を、どうやって設計するのか。
</div>

### 2.1 シャノンの2つの原理

1949 年にシャノンは、良い暗号に必要な2つの性質を挙げました。

| 原理 | 意味 | 欠けているとどうなるか | 担当する部品 |
| --- | --- | --- | --- |
| 混乱（confusion） | 鍵と暗号文の関係を複雑にする | 暗号文から鍵を方程式で解かれる | 非線形な変換（S-box） |
| 拡散（diffusion） | 平文の1ビットの影響を、暗号文全体に広げる | 平文の統計が暗号文に残る（第2回の頻度分析） | ビットの並べ替え、行列による混ぜ合わせ |

1回では弱い変換でも、混乱と拡散を交互に何度も繰り返すと、全体として強くなります。現代のブロック暗号は、すべてこの「ラウンドの繰り返し」でできています。

問題は、繰り返す変換が全部逆算できないといけないことです。逆算できる変換だけで混乱を作るのは、意外と難しいんです。その解決策が2つあります。

### 2.2 Feistel 構造: 逆算できない関数から置換を作る

Feistel 構造は、ブロックを左右の半分に分け、次の操作を繰り返します。

```
L_{i+1} = R_i
R_{i+1} = L_i ⊕ F(R_i, k_i)
```

ここが巧みなところで、ラウンド関数 F は逆算できなくてもかまいません。右半分 R_i はそのまま次の左半分になって残るので、復号する側は F(R_i, k_i) をもう一度計算して、XOR を外すだけで L_i に戻せるんです。下の図の F は、わざと下位2ビットを捨てる「逆算できない関数」にしてありますが、それでも正しく復号できることを確かめてください。

<figure class="widget" data-widget="feistel"></figure>

<div class="box thm" markdown="1">
**Luby-Rackoff の定理** F が PRF なら、独立なラウンド鍵を使った3ラウンドの Feistel 構造は PRP になり、4ラウンドなら強い PRP になる。
</div>

この定理は、「PRF から PRP を作れる」ことを示しています。旧標準の DES は、64 ビットのブロックを 16 ラウンドの Feistel 構造で暗号化していました。

### 2.3 SPN 構造: 全部を逆算できる部品で作る

もう1つの方法は、置換（Substitution）と並べ替え（Permutation）を交互に重ねる SPN 構造です。各部品はすべて逆算できるように作り、ブロック全体を毎ラウンド変換します。AES はこちらです。

| | Feistel | SPN |
| --- | --- | --- |
| 1ラウンドで変わる部分 | 半分 | 全体 |
| ラウンド関数の条件 | 逆算できなくてよい | 各部品が逆算できる必要がある |
| 復号 | 暗号化とほぼ同じ回路（鍵の順を逆にするだけ） | 逆の部品が別に必要 |
| 代表例 | DES、Camellia（変形） | AES |

<div class="sum" markdown="1">
- ブロック暗号は、混乱（非線形）と拡散（広げる）を交互に何度も繰り返して作る
- Feistel 構造は、逆算できない関数からでも逆算できる置換を作れる（PRF から PRP）
- SPN 構造は、全部を逆算できる部品で作り、毎ラウンド全体を変える。AES はこちら
- 次の §3 で、AES の中で実際に何が起きているかを1手ずつ追う
</div>

## §3 AES: 実物の中を覗く

<div class="q" markdown="1">
世界標準のブロック暗号 AES は、16 バイトを暗号化するあいだに何をしているのか。各操作はなぜ必要なのか。
</div>

### 3.1 AES の概要

AES は、ベルギーの Daemen と Rijmen が設計した Rijndael を、米国標準技術研究所（NIST）が公募の末に 2001 年に標準化したものです（FIPS 197）。

| 項目 | 値 |
| --- | --- |
| ブロック長 | 128 ビット（16 バイト） |
| 鍵長 | 128 / 192 / 256 ビット |
| ラウンド数 | 10 / 12 / 14 |
| 構造 | SPN |
| 計算の舞台 | 第1回 §5.6 の GF(2^8)（1 バイト = 1 要素） |

16 バイトは、4×4 のマス目（状態）に縦の順に並べて扱います。

### 3.2 1ラウンドの4つの操作

各ラウンドは4つの操作でできていて、それぞれに役割があります。

| 操作 | やること | 役割 | 欠けるとどうなるか |
| --- | --- | --- | --- |
| SubBytes | 各バイトを S-box で置き換える | 混乱（唯一の非線形部分） | 全体が線形になり、連立方程式で解ける |
| ShiftRows | 行ごとにバイトを左に回す | 拡散（列をまたいで散らす） | 4つの列が独立した小さな暗号に分かれてしまう |
| MixColumns | 各列の4バイトを行列で混ぜる | 拡散（列の中で広げる） | 1 バイトの変化が他のバイトに伝わらない |
| AddRoundKey | ラウンド鍵と XOR する | 鍵を混ぜる | 鍵なしで誰でも計算できる |

下の図で、FIPS 197 付録 B の例を1手ずつ進めてください。色の付いたマスは、直前の操作で値が変わったバイトです。SubBytes と AddRoundKey は全マスを変え、ShiftRows は1行目以外を動かし、MixColumns は列全体を書き換えるのが見えます。

<figure class="widget" data-widget="aes-round"></figure>

最終ラウンドに MixColumns がないのは、復号の手順を暗号化と対称な形に揃えるためで、安全性には影響しません。

### 3.3 拡散を確かめる: 雪崩効果

良いブロック暗号は、平文の1ビットを変えると、暗号文の約半分のビットが変わります（雪崩効果）。AES ではそれが何ラウンドで起きるかを見てみます。

<figure class="widget" data-widget="aes-avalanche"></figure>

1 ビットの違いは、1ラウンド目の SubBytes で1バイトに、MixColumns で1列の4バイトに広がります。2ラウンド目の ShiftRows で4つの列に散り、MixColumns で全16バイトに広がります。2ラウンドで全体に行き渡るように設計されている（wide trail 戦略）ので、10ラウンドは十分な余裕を持たせた数です。

### 3.4 AES はどれくらい安全か

| 観点 | 現状 |
| --- | --- |
| 最良の鍵回復攻撃 | biclique 攻撃で約 2^126（AES-128）。総当たりより数倍速いだけで、実用的な脅威ではない |
| 差分解読・線形解読 | S-box と wide trail 戦略により、ラウンド数に対して十分な余裕がある |
| 量子計算機 | Grover のアルゴリズムで鍵の総当たりが平方根程度に速くなる。AES-256 なら十分な余裕がある（第8回） |
| 実装への攻撃 | 表引き（ここでの実装のような）はキャッシュのタイミングで鍵が漏れうる。実務では CPU の AES 命令（AES-NI など）や、定数時間の実装を使う（第7回） |

AES の数学的な強さに不安はなく、問題が起きるのはほぼすべて「使い方」と「実装」です。それが次の §4 のテーマです。

<div class="sum" markdown="1">
- AES は 4×4 バイトの状態に、SubBytes（混乱）、ShiftRows と MixColumns（拡散）、AddRoundKey（鍵）を10ラウンド繰り返す
- 2ラウンドで1ビットの違いが全体に広がり、10ラウンドは十分な余裕
- AES 自体の強さに不安はない。問題は「どう使うか」と「どう実装するか」に移る
</div>

## §4 運用モード: 16 バイトの部品で長いデータを暗号化する

<div class="q" markdown="1">
AES は 16 バイトしか暗号化できない。それを使って長いデータを IND-CPA 安全に暗号化するには、どうつなげばよいか。
</div>

### 4.1 つなぎ方の3つの代表

ブロック暗号をどうつなぐかの設計を、運用モードと呼びます。代表的な3つの構造を見比べてください。

<figure class="widget" data-widget="modes-diagram"></figure>

### 4.2 ECB: そのまま並べると何が起きるか

いちばん素朴なのは、データを 16 バイトずつに切って、それぞれを独立に暗号化する ECB です。第2回 §4.4 で、決定的な暗号化は IND-CPA 安全になれないと示しました。ECB はまさにその典型で、同じ平文ブロックは同じ暗号文ブロックになります。画像で見ると一目瞭然です。

<figure class="widget" data-widget="ecb-image"></figure>

<div class="box warn" markdown="1">
**Java の落とし穴** Java で Cipher.getInstance("AES") とモードを省略すると、標準のプロバイダでは "AES/ECB/PKCS5Padding" になります。モードとパディングは必ず明示し、今なら "AES/GCM/NoPadding"（第4回）を使ってください。
</div>

### 4.3 CBC: 前の暗号文を混ぜる

CBC は、各平文ブロックに、1つ前の暗号文ブロックを XOR してから暗号化します。最初のブロックには、代わりに初期化ベクトル（IV）を XOR します。

```
C_1 = E_k(P_1 ⊕ IV),   C_i = E_k(P_i ⊕ C_{i−1})
P_i = D_k(C_i) ⊕ C_{i−1}
```

同じ平文ブロックでも、前の暗号文が違えば違う暗号文になるので、ECB の問題は消えます。

<div class="box thm" markdown="1">
**定理（CBC）** E が PRP で、IV を毎回ランダムに（攻撃者が予測できないように）選ぶなら、CBC は IND-CPA 安全である。攻撃者の優位性は、おおむね q²/2^n（q は暗号化したブロックの総数）で抑えられる。
</div>

条件の「予測できない」が重要です。

| IV の選び方 | 安全か | 理由 |
| --- | --- | --- |
| 毎回ランダム | ○ | 定理の条件どおり |
| 固定値 | × | 最初のブロックが ECB と同じになる |
| カウンタ（1, 2, 3…） | × | 予測できるので、攻撃者が次の平文を工夫して、推測を確かめられる |
| 前のメッセージの最後の暗号文 | × | TLS 1.0 がこれをしていて、BEAST 攻撃（2011年）で破られた |

また、データの長さを 16 バイトの倍数に揃えるパディング（PKCS#7: 足りないバイト数 k の値 k を k 個並べる）が必要です。このパディングの検査が、第4回のパディングオラクル攻撃の入口になります。

### 4.4 CBC は改ざんを防がない

IND-CPA は「秘匿性」の定義で、「改ざんされないこと」は何も言っていません。CBC の復号式 P_i = D_k(C_i) ⊕ C_{i−1} を見ると、C_{i−1} を変えると P_i が同じだけ変わることが分かります。鍵を知らない攻撃者でも、平文の中身を狙いどおりに書き換えられるんです。

<figure class="widget" data-widget="cbc-flip"></figure>

これは CBC の欠陥というより、「暗号化は秘匿性しか守らない」という一般的な事実の表れです。CTR モードでは、暗号文の1ビットを反転すると、同じ位置の平文の1ビットがそのまま反転します。

### 4.5 CTR: カウンタからワンタイムパッドを作る

CTR は、ノンスとカウンタの組を E_k に通して鍵の列を作り、平文と XOR します。

```
C_i = P_i ⊕ E_k(N ‖ i)
```

第2回の疑似ワンタイムパッドの「G(s)」を、「E_k に毎回違う入力を入れた出力」に置き換えたものです。E_k が PRF なら、入力が違う限り、出てくる鍵の列は独立な乱数と見分けがつきません。

<div class="box thm" markdown="1">
**定理（CTR）** E が PRF で、同じ鍵のもとで (ノンス, カウンタ) の組が二度と繰り返されないなら、CTR は IND-CPA 安全である。
</div>

条件は「ノンスが重複しないこと」です。重複すると、第2回 §2.3 のワンタイムパッドの鍵の再利用と同じことになり、2つの平文の XOR が漏れます。

### 4.6 モードの比較

| モード | IND-CPA | 条件 | 並列化 | パディング | 改ざん検知 |
| --- | --- | --- | --- | --- | --- |
| ECB | × | — | ○ | 要る | × |
| CBC | ○ | IV が毎回ランダムで予測不能 | 復号のみ | 要る | × |
| CTR | ○ | ノンスとカウンタが重複しない | ○ | 不要 | × |
| GCM（第4回） | ○ | ノンスが重複しない | ○ | 不要 | ○ |

ストレージ（ディスク全体の暗号化）には、セクター単位で書き換えられる XTS という専用のモードがあります（IEEE 1619、NIST SP 800-38E）。ただし XTS も改ざんは検知しません。

<div class="sum" markdown="1">
- ECB は同じ平文ブロックが同じ暗号文になり、使ってはいけない
- CBC は「予測できない IV」、CTR は「重複しないノンス」という条件のもとで IND-CPA 安全
- どちらも改ざんは防がない。CBC では前のブロックをいじって次のブロックを書き換えられる
- 秘匿性と改ざん検知を同時に満たす方法は第4回で扱う。その前に §5 で、ブロック暗号を使わない暗号化を見る
</div>

## §5 ストリーム暗号: もう1つの作り方

<div class="q" markdown="1">
ブロック暗号を経由せず、PRG で直接鍵の列を作る方法はあるか。それはどんなときに選ばれるのか。
</div>

CTR モードは、ブロック暗号を使って鍵の列を作るものでした。最初から「鍵とノンスから長い鍵の列を作る」専用の関数を設計したものがストリーム暗号です。第2回の PRG に、ノンスの入力を足したものと考えると分かりやすいです。

### 5.1 RC4 の失敗

| 年 | 出来事 |
| --- | --- |
| 1987 | RC4 が設計される。単純で速く、SSL/TLS や Wi-Fi（WEP）で広く使われた |
| 2001 | 鍵の列の最初の部分に偏りがあることが分かり、WEP が実用的に破られる |
| 2013〜2015 | TLS での RC4 の偏りを使った平文の復元が実証され、RFC 7465 で TLS での使用が禁止される |

出力に偏りがあることは、第2回の言葉で言えば「識別器が作れる」、つまり PRG ではないということです。

### 5.2 ChaCha20

現在のストリーム暗号の標準は ChaCha20 です（Bernstein が設計した Salsa20 の改良版、RFC 8439）。

| 項目 | 値 |
| --- | --- |
| 鍵 | 256 ビット |
| ノンス | 96 ビット |
| ブロックカウンタ | 32 ビット（1 ブロック 64 バイト） |
| 構造 | 20 ラウンドの加算・回転・XOR（ARX） |

ChaCha20 は加算・ビット回転・XOR だけでできているので、表引きがなく、普通のソフトウェアでも自然に定数時間で実装できます。AES 専用命令がない CPU（古いスマートフォンなど）では、AES より速く、しかもタイミング攻撃の心配がありません。TLS 1.3 では、AES-GCM と並ぶ選択肢になっています（第4回の ChaCha20-Poly1305）。

条件は CTR と同じで、同じ鍵でノンスを重複させてはいけません。

<div class="sum" markdown="1">
- ストリーム暗号は、鍵とノンスから鍵の列を作る専用の PRG。出力に偏りがあれば破られる（RC4）
- ChaCha20 は表引きがなく、ソフトウェアでも速く、定数時間で実装しやすい
- 使い方の条件は CTR と同じで、ノンスの重複は厳禁
</div>

## §6 実務の選択

<div class="q" markdown="1">
結局、実務で共通鍵暗号を使うときは、何を選び、何を避ければよいのか。
</div>

| 用途 | 選ぶもの | 避けるもの |
| --- | --- | --- |
| 通信やデータの暗号化（一般） | AES-GCM または ChaCha20-Poly1305（第4回）。秘匿性と改ざん検知を同時に満たす | ECB。CBC や CTR の単体使用（改ざんを防げない） |
| ディスク・ストレージ全体 | AES-XTS（OS やストレージ製品の機能を使う） | 自作のモード |
| 古いシステムとの互換 | CBC を使うなら、ランダムな IV と、Encrypt-then-MAC（第4回）で改ざん検知を足す | 固定 IV、予測できる IV |
| ブロック長 | 128 ビット（AES） | 64 ビット（3DES、Blowfish） |
| 鍵長 | AES-128 で現在は十分。量子計算機を見越すなら AES-256 | DES（56 ビット鍵） |

### 実装レビューで見るポイント

1. モードが明示されているか（Java の Cipher.getInstance("AES") のような省略がないか）
2. IV やノンスが、毎回乱数（CBC）または重複しない値（CTR、GCM）になっているか。定数や、鍵から作った値になっていないか
3. 同じ鍵で暗号化する量に上限を設け、鍵を定期的に替えているか
4. 暗号化だけで済ませていないか。改ざん検知（MAC や AEAD）があるか
5. 暗号化の部品を自作していないか。標準ライブラリの高水準な API を使っているか

<div class="sum" markdown="1">
- 現在の標準は、AES か ChaCha20 を、認証付き暗号（第4回）として使うこと
- レビューでは「モードの明示」「IV とノンスの条件」「鍵を替える量」「改ざん検知の有無」を確かめる
</div>

## 演習問題

### A. 確認

1. PRF と PRP の違いを1文で述べ、両者が見分けられるようになるまでの問い合わせ回数の目安を、ブロック長 n で答えよ
2. 64 ビットのブロック暗号で、同じ鍵のまま 1 Gbps の通信を何時間続けると、2^32 ブロックに達するか
3. Feistel 構造で、ラウンド関数 F が逆算できなくても復号できる理由を説明せよ
4. AES の SubBytes を取り除くと何が起きるか。理由とともに答えよ
5. CBC の IV に「1 から順に増えるカウンタ」を使ってはいけない理由を説明せよ

### B. 攻撃と証明

6. 1ラウンドの Feistel 構造が PRP でないことを、識別器を作って示せ（ヒント: 出力の左半分を見る）
7. CTR モードで、同じノンスを使って2つの平文 P, P′ を暗号化した。暗号文から何が分かるか。P の一部が既知のとき、P′ の対応する部分を求めよ
8. CBC の暗号文 (IV, C₁, C₂) について、IV だけを書き換えると何が起きるか。C₁ を書き換えた場合と比べよ

### C. 実装

9. 第1回で作った gmul を使って AES-128 を実装し、FIPS 197 付録 B のテストベクタ（平文 3243f6a8…、鍵 2b7e1516…、暗号文 3925841d…）で検証せよ
10. ECB の暗号文から、平文の繰り返しを検出するプログラムを書け（Cryptopals Set 1 の問題 8）
11. CBC のビット反転で、"role=guest" を含む平文を "role=admin" に書き換える攻撃を実装せよ（Cryptopals Set 2 の問題 16）

## 解答と解説

### A. 確認

1. PRF の出力は重なりうるが、PRP（置換）の出力は重ならない。見分けられるのは約 2^(n/2) 回から
2. 1 Gbps は毎秒約 2^30 ビット = 2^24 ブロック（64 ビット = 2^6 ビット）。2^32 / 2^24 = 2^8 = 256 秒、つまり約 4 分強。長時間の接続では簡単に達する
3. 右半分 R_i がそのまま次の左半分として残るので、復号側は F(R_i, k_i) を再計算でき、XOR を外して L_i を取り戻せる。F の逆関数は一度も使わない
4. AES 全体が GF(2) 上の線形（アフィン）変換になる。平文と暗号文の組がいくつかあれば、連立一次方程式を解いて鍵に相当する情報を求められ、破られる。S-box は唯一の非線形部分
5. 次に使う IV を攻撃者が予測できるので、平文の最初のブロックを「予測した IV ⊕ 以前の IV ⊕ 推測した平文」のように工夫して暗号化させ、暗号文を比べることで推測が当たっているか確かめられる。BEAST 攻撃と同じ原理

### B. 攻撃と証明

6. 1ラウンドでは出力の左半分 = 入力の右半分（L₁ = R₀）。識別器は入力 (L, R) を問い合わせ、出力の左半分が R と一致すれば「Feistel」と答える。ランダムな置換なら一致する確率は 2^(−n/2) 程度なので、優位性はほぼ 1
7. 同じ鍵の列 S を使うので、C ⊕ C′ = P ⊕ P′。P の一部が既知なら、その部分で P′ = C ⊕ C′ ⊕ P と求まる（第2回のクリブと同じ）
8. IV を書き換えると、P₁ = D(C₁) ⊕ IV の P₁ が XOR した分だけ変わり、ほかのブロックは影響を受けない（壊れるブロックがない）。C₁ を書き換えると P₂ が変わる代わりに、P₁ = D(C₁′) ⊕ IV が予測できない値に壊れる

### C. 実装のポイント

- 問題9: ラウンド鍵の最後（10ラウンド目）が d014f9a8c9ee2589e13f0cc8b6630ca6 になるかで、鍵拡張を先に確かめると切り分けやすくなります
- 問題10: 暗号文を 16 バイトずつに区切って、重複するブロックがあるかを数えるだけで見つかります
- 問題11: 区切り文字（; や =）をエスケープする実装でも、ビット反転なら入力にない文字を作れる点がポイントです
