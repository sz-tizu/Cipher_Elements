    暗号文が途中で書き換えられていないことを、どうやって保証するのか。

    §1 改ざん検知に何が要るか

    受け取ったデータが途中で書き換えられていないと確かめるには、どんな仕組みが必要か。チェックサムやハッシュ値を添えるだけでは足りないのか。

    データに「しるし」を添えて送り、受け取った側がしるしを確かめる、という形はどれも同じです。違うのは、そのしるしを誰が作れるかです。

    しるし 作れる人 守れるもの 守れないもの
    CRC などのチェックサム 誰でも 偶然の誤り（ノイズ） 意図的な改ざん。攻撃者はデータを変えてチェックサムも計算し直せる
    ハッシュ値（SHA-256 など） 誰でも 別経路で正しいハッシュ値が届くなら、その一致 ハッシュ値と一緒に送ると、攻撃者は両方を差し替えられる
    MAC（この回） 鍵を共有する人だけ 意図的な改ざん、なりすまし 送信者と受信者のどちらが作ったか（両方とも鍵を持つ）
    デジタル署名（第6回） 秘密鍵を持つ1人だけ 意図的な改ざん、第三者への証明 —

    攻撃者が計算し直せないしるしには、鍵が要ります。この回の主役は、共通鍵で作るしるし、MAC です。その材料として、まずハッシュ関数を押さえます。

    • 改ざん検知のしるしは、攻撃者が計算し直せないもの、つまり鍵を持つ人だけが作れるものでなければならない
    • 共通鍵で作るしるしが MAC、秘密鍵で作るしるしが署名（第6回）
    • 次の §2 では MAC の材料になるハッシュ関数と、その安全性の定義を見る

    §2 ハッシュ関数: どんなデータも短く要約する

    「安全なハッシュ関数」とは、具体的にどんな攻撃に耐えるものなのか。それぞれの攻撃にはどれくらいの手間がかかるのか。

    2.1 3つの安全性

    ハッシュ関数 H は、任意の長さのデータを固定長（SHA-256 なら 256 ビット）に要約します。入力のほうが圧倒的に多いので、同じ出力になる入力の組は必ず存在します。安全とは、それを「見つけられない」ことです。何を与えられて何を探すかで、3つの安全性に分かれます。

    安全性 攻撃者に与えるもの 攻撃者が探すもの 一般的な攻撃の手間（n ビット出力） 必要になる場面
    原像困難性 出力 y H(x) = y となる x 2^n パスワードの保存、コミットメント
    第二原像困難性 入力 x H(x′) = H(x) となる別の x′ 2^n ファイルの改ざん検知（元のファイルは決まっている）
    衝突困難性 なし H(x) = H(x′) となる任意の組 2^(n/2)（誕生日攻撃） 署名（第6回）、証明書

    衝突は、探す側が両方の入力を自由に選べるので、第1回 §6 の誕生日の確率から約 2^(n/2) で見つかります。原像は狙った1つの値を当てる必要があるので、2^n かかります。この差を、下の図で実際に計算して確かめてください。

    2.2 現在の状況

    ハッシュ関数 出力 衝突困難性の現状 実務での扱い
    MD5 128 ビット 2004年に衝突が発見され、今は数秒で作れる。偽の証明書の作成にも使われた 安全性が必要な用途では使用禁止
    SHA-1 160 ビット 2017年に実際の衝突（SHAttered）、2020年に選択プレフィックス衝突 署名や証明書では使用禁止
    SHA-256、SHA-512（SHA-2） 256、512 ビット 知られた有効な攻撃なし 標準。ただし §3 の長さ拡張に注意
    SHA-3（Keccak） 224〜512 ビット 知られた有効な攻撃なし SHA-2 とは別の構造（スポンジ）の標準

    衝突困難性が先に崩れ、原像困難性はずっと後まで残る、というのが歴史のパターンです。MD5 や SHA-1 でも、原像を実用的に求める方法はまだありません。

    • ハッシュの安全性は、原像・第二原像・衝突の3つ。衝突だけ手間が 2^(n/2) と小さい
    • MD5 と SHA-1 は衝突が実際に作られ、署名などには使えない。標準は SHA-2 と SHA-3
    • では、ハッシュに鍵を混ぜれば MAC になるのか。次の §3 で、素朴なやり方が失敗する例を見る

    §3 長さ拡張攻撃: 素朴な MAC の失敗

    鍵を前に付けてハッシュを取る H(鍵 ‖ メッセージ) は、鍵を知らない人には作れない「しるし」になるか。

    3.1 SHA-2 の作り: Merkle-Damgård 構造

    MD5、SHA-1、SHA-2 は、同じ設計（Merkle-Damgård 構造）でできています。メッセージを 64 バイトずつのブロックに区切り、圧縮関数 f で内部状態を順に更新していき、最後の内部状態をそのまま出力します。

    ここで問題なのは、出力が「最後の内部状態そのもの」であることです。出力を知っている人は、その続きから計算を再開できます。「長さ拡張を表示する」を押すと、何が起きるかが分かります。

    3.2 実際に偽造する

    サーバが、鍵 k を使って tag = SHA-256(k ‖ m) をメッセージ m に添えているとします。攻撃者は m と tag を知っていて、k は知りません。それでも、m の後ろに好きな文字列を付け足したメッセージの正しいタグを作れます。

    攻撃者がやったのは、次の3つだけです。

    1. 元のメッセージの後ろに、SHA-256 が内部で付けるはずだったパディング（0x80、0 の並び、長さ）を付ける。そのためには鍵の長さが必要だが、1〜64 を全部試せば済む
    2. tag を内部状態として読み込み、付け足したい文字列の分だけ圧縮関数を回す
    3. その結果を、新しいメッセージのタグとして提出する

    3.3 防ぎ方

    方法 長さ拡張に強い理由
    HMAC（§4） 外側にもう一度ハッシュを掛けるので、出力から内側の状態に戻れない
    SHA-3、KMAC スポンジ構造で、出力に使わない内部状態（capacity）が隠されている
    SHA-512/256 などの切り詰め版 出力が内部状態の一部しか含まないので、続きを計算できない

    H(k ‖ m) のように自作で鍵を混ぜるのは避け、標準の MAC（HMAC など）を使う、というのが実務の答えです。

    • Merkle-Damgård 構造のハッシュは、出力が最後の内部状態そのものなので、続きを計算できてしまう
    • そのため H(鍵 ‖ m) は MAC にならない。鍵を知らなくても、メッセージを付け足したタグが作れる
    • 防ぐには HMAC などの、MAC として設計・証明されたものを使う。次の §4 で、MAC の定義と HMAC を見る

    §4 MAC: 鍵付きの改ざん検知

    MAC が「安全」とは、正確には何を意味するのか。それを満たす MAC は、どう作るのか。

    4.1 MAC の安全性: 偽造できないこと

    MAC は、鍵 k とメッセージ m からタグ t = MAC(k, m) を作り、受信者は同じ鍵で t を確かめます。安全性は、第2回と同じくゲームで定義します。攻撃者には、好きなメッセージにタグを付けてもらえる能力（タグ生成オラクル）を与え、まだタグをもらっていないメッセージの正しいタグを作れたら勝ち、とします。

    定義（EUF-CMA 安全） タグ生成オラクルを使える、どんな PPT の攻撃者 A についても、新しいメッセージの正しいタグを作れる確率が無視できるとき、MAC は EUF-CMA 安全（選択メッセージ攻撃のもとで存在的偽造不能）であるという。

    「存在的」とは、意味のあるメッセージでなくても、どんな新しいメッセージでも偽造できたら負け、という厳しい条件のことです。さらに、既存のメッセージに別の正しいタグを作ることも禁じたものを、強い偽造不能性（SUF-CMA）と呼びます。§5 の Encrypt-then-MAC では、こちらが必要になります。

    4.2 HMAC

    いちばん広く使われている MAC が HMAC です（RFC 2104）。ハッシュ関数を2回、鍵を内側と外側で混ぜて使います。

    HMAC(K,m)=H((K⊕opad)∥H((K⊕ipad)∥m))

    外側のハッシュが内側の結果を包んでいるので、§3 の長さ拡張は効きません。HMAC は、圧縮関数が PRF として振る舞うという仮定のもとで、PRF（したがって安全な MAC）であることが証明されています。

    4.3 そのほかの MAC

    MAC 材料 特徴
    HMAC-SHA256 ハッシュ関数 汎用。TLS の鍵導出、JWT（HS256）、API の署名などで広く使われる
    CBC-MAC ブロック暗号 長さが固定のときだけ安全。可変長では偽造できる
    CMAC ブロック暗号 CBC-MAC の可変長の問題を直したもの（NIST SP 800-38B）
    GHASH、Poly1305 有限体の多項式 1回限りの鍵で非常に速い。暗号化と組み合わせて AEAD の中で使う（§6）

    4.4 検証は定数時間で比較する

    タグの検証で、先頭から1バイトずつ比べて、違ったらすぐ返す実装（Java の Arrays.equals、文字列の equals など）を使うと、何バイト目まで合っていたかが応答時間に出てしまいます。攻撃者は、1バイトずつ正しいタグを当てられます（第7回で実演します）。比較は、最後まで同じ時間をかける関数で行います。

    言語 定数時間の比較
    Java MessageDigest.isEqual
    Python hmac.compare_digest
    Go crypto/subtle.ConstantTimeCompare
    • MAC の安全性は、タグを付けてもらえる攻撃者でも、新しいメッセージのタグを偽造できないこと（EUF-CMA）
    • HMAC はハッシュを2回使うことで長さ拡張を防ぎ、PRF として証明されている
    • タグの検証は定数時間で比較する
    • MAC で改ざん検知、暗号化で秘匿。では2つをどう組み合わせればよいのか。次の §5 で、その順序が安全性を左右することを見る

    §5 暗号化と MAC の組み合わせ: 順序とパディングオラクル

    暗号化と MAC を両方使うとき、「先に暗号化するか、先に MAC を付けるか」で何が変わるのか。

    5.1 3つの組み合わせ方

    組み合わせ方 送るもの 一般的な安全性 使われた例
    Encrypt-and-MAC Enc(m) と MAC(m) 保証されない。MAC から平文の情報が漏れうる SSH
    MAC-then-Encrypt Enc(m ‖ MAC(m)) 暗号化の方式次第。CBC と組み合わせると危険 SSL/TLS 1.2 以前の CBC モード
    Encrypt-then-MAC Enc(m) と MAC(Enc(m)) 安全（下の定理） IPsec、TLS の拡張（RFC 7366）

    定理（Bellare-Namprempre、2000年） 暗号化が IND-CPA 安全で、MAC が強い偽造不能性（SUF-CMA）を満たすなら、Encrypt-then-MAC は IND-CCA 安全で、暗号文の改ざんも検知できる。

    直感的には、Encrypt-then-MAC では受信者がまずタグを確かめ、改ざんされた暗号文は復号せずに捨てます。攻撃者が暗号文をいじっても、復号処理そのものに届かないので、復号の振る舞いから何も学べません。逆に MAC-then-Encrypt では、改ざんされた暗号文でもまず復号してしまいます。その途中の反応が漏れると、次に見る攻撃が成立します。

    5.2 パディングオラクル攻撃

    CBC には、平文の長さを 16 バイトの倍数に揃えるパディングがありました（PKCS#7: 足りないバイト数 k の値 k を k 個並べる）。MAC-then-Encrypt で CBC を使うサーバは、受け取った暗号文を復号したあと、まずパディングが正しい形かを確かめ、次に MAC を確かめます。このとき、2つの失敗を区別できる応答（エラーの種類、処理時間）を返してしまうと、攻撃者は「パディングが正しいか」という1ビットの情報を得られます。この1ビットを返してくれる存在を、パディングオラクルと呼びます。

    原理は、CBC の復号式 P = D_k(C) ⊕ C′（C′ は1つ前の暗号文ブロック）にあります。

    1. 攻撃者は、解読したいブロック C の前に、自分で作った偽のブロック C′ を置いて送る
    2. サーバは D_k(C) ⊕ C′ を計算して、パディングを確かめる。D_k(C) は鍵がないと計算できない「中間値」
    3. 攻撃者は C′ の最後のバイトを 0〜255 まで変えながら送り、「パディングが正しい」と言われる値を探す
    4. 正しいと言われたら、復号結果の最後のバイトは 0x01 のはずなので、中間値の最後のバイト = その値 ⊕ 0x01 と分かる
    5. 本物の前のブロックと XOR すれば、平文の最後のバイトが分かる。次は末尾 2 バイトを 0x02 0x02 にするように調整して、1つ前のバイトへ進む

    1 バイトあたり最大 256 回、平均 128 回の問い合わせで済むので、16 バイトのブロックは数千回の問い合わせで丸ごと読めます。下の図で、実際に解いてみてください。サーバの実装を AEAD に切り替えると、攻撃が一歩も進まなくなることも確かめてください。

    5.3 実際に起きたこと

    年 攻撃 何が漏れたか
    2002 Vaudenay のパディングオラクル攻撃 CBC のパディング検査の成否
    2010 ASP.NET のパディングオラクル Web アプリの暗号化された状態データ。サーバの設定ファイルの読み出しにまで発展した
    2013 Lucky Thirteen エラーの種類は同じでも、パディング検査と MAC 計算の処理時間の差
    2014 POODLE SSL 3.0 の CBC パディングの検査が不完全だったこと

    教訓は2つあります。1つ目は、エラーメッセージを揃えても、処理時間の差で同じことが起きる（Lucky Thirteen）ことです。2つ目は、これらはすべて「復号してから検証する」構造が原因で、Encrypt-then-MAC や AEAD なら原理的に起きないことです。TLS 1.3 は、この反省から CBC モードをすべて廃止し、AEAD だけにしました。

    • 暗号化と MAC は、Encrypt-then-MAC（暗号文に MAC を付け、検証してから復号）が安全
    • 「復号してから検証する」構造では、復号処理の反応（エラーの種類、時間）が漏れ、パディングオラクル攻撃で平文が読まれる
    • 組み合わせ方を自分で選ぶこと自体が事故のもとになる。次の §6 で、最初から両方をまとめて設計した AEAD を見る

    §6 AEAD: 秘匿と改ざん検知を1つにまとめる

    暗号化と MAC を毎回正しく組み合わせる代わりに、最初から両方を満たす部品として使える標準はあるか。その使い方の条件は何か。

    6.1 AEAD とは

    認証付き暗号（AEAD: Authenticated Encryption with Associated Data）は、次のインターフェースを持つ1つの部品です。

    暗号化: (C, tag) = Seal(K, ノンス N, 平文 P, 関連データ AD)
復号  : P または「失敗」 = Open(K, N, C, tag, AD)
    守るもの 平文 P 関連データ AD
    秘匿性（読まれない） ○ ×（平文のまま送る）
    完全性（変えられない） ○ ○

    関連データは、暗号化はしないが改ざんは検知したいデータです。たとえばパケットのヘッダ（宛先やシーケンス番号）は、中継機器が読めないと困るので暗号化できませんが、書き換えられては困ります。そういうものを AD に入れます。

    AEAD の安全性は、「IND-CPA（秘匿性）」と「暗号文の完全性（改ざんした暗号文は必ず『失敗』になる）」の両方を満たすこととして定義され、両方を満たせば IND-CCA も満たします。

    6.2 2つの標準

    AES-GCM ChaCha20-Poly1305
    暗号化の部分 AES の CTR モード（第3回） ChaCha20（第3回 §5）
    改ざん検知の部分 GHASH（GF(2^128) の多項式） Poly1305（素数 2^130 − 5 を法とする多項式）
    ノンス 96 ビット 96 ビット
    速さ AES 専用命令がある CPU で非常に速い 専用命令なしでも速く、定数時間で実装しやすい
    規格 NIST SP 800-38D RFC 8439

    どちらも、第3回の CTR 型の暗号化に、第4回の Carter-Wegman 型の MAC を、暗号化した後に掛ける（Encrypt-then-MAC の形）構造です。TLS 1.3 では、この2つが中心の選択肢です。

    6.3 ノンスの条件と、破ったときに壊れるもの

    AEAD のほぼ唯一の使用条件は、「同じ鍵で、同じノンスを二度と使わない」ことです。破ると、次のように壊れます。

    壊れるもの AES-GCM ChaCha20-Poly1305
    秘匿性 同じ鍵の列が使われ、2つの平文の XOR が漏れる（第2回のワンタイムパッドの再利用） 同じ
    完全性 認証鍵 H が多項式の根として求まり、以後、好きなメッセージを偽造できる 1回限りの Poly1305 鍵が再利用され、偽造が可能になる

    GCM のノンス再利用は、秘匿性だけでなく改ざん検知まで壊す点が重大です。ノンスの作り方は2通りあります。

    作り方 条件 注意
    カウンタ（0, 1, 2, …） 状態を正しく保存し、再起動やバックアップからの復元で巻き戻さない 複数のサーバが同じ鍵を使うと重複しやすい
    96 ビットの乱数 誕生日の確率で、同じ鍵での暗号化回数に上限がある NIST は 2^32 回までとしている

    ノンスの管理が難しい場面のために、重複しても被害が限定される AES-GCM-SIV（RFC 8452）もあります。ノンスが重複しても、漏れるのは「同じ平文を同じノンスで暗号化した」という事実だけです。

    6.4 Java での正しい使い方

    // 鍵は KeyGenerator（または KDF）で作り、ノンスは暗号化ごとに必ず新しくする
byte[] nonce = new byte[12];
new SecureRandom().nextBytes(nonce);                 // 乱数ノンス（同じ鍵で 2^32 回まで）
Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
cipher.init(Cipher.ENCRYPT_MODE, key, new GCMParameterSpec(128, nonce));
cipher.updateAAD(header);                            // 関連データ（暗号化しないが改ざんを検知）
byte[] ct = cipher.doFinal(plaintext);              // 末尾に 16 バイトのタグが付く
// 送るもの: nonce ‖ ct（ノンスは秘密ではない）

    Java の GCM 実装は、同じ Cipher オブジェクトで同じ鍵とノンスの組を再び使おうとすると、例外で止めてくれます。ただし、オブジェクトをまたいだ重複までは検知できないので、ノンスの生成は設計で保証する必要があります。

    • AEAD は、秘匿性と改ざん検知を1つにまとめた部品。関連データは暗号化せずに改ざんだけを検知する
    • 標準は AES-GCM と ChaCha20-Poly1305。どちらも CTR 型の暗号化に MAC を後から掛ける構造
    • 唯一にして最大の条件は「同じ鍵でノンスを重複させない」。GCM では、破ると改ざん検知まで壊れる
    • 最後の §7 では、AEAD に渡す鍵そのものを、別の鍵やパスワードから作る方法を見る

    §7 KDF とパスワード: 鍵を作る

    AEAD に渡す鍵は、どうやって作るのか。共有した秘密値や、人間が覚えるパスワードから鍵を作るときは、何に気をつければよいのか。

    7.1 2種類の材料

    材料 例 性質 使うもの
    高エントロピーだが形が不揃いな秘密 Diffie-Hellman の共有値（第5回）、マスター鍵 推測はできないが、偏りがあったり長さが合わなかったりする HKDF
    低エントロピーの秘密 人間が覚えるパスワード 候補を順に試せば当たりうる パスワードハッシュ（Argon2、scrypt、bcrypt、PBKDF2）

    7.2 HKDF: 抽出してから展開する

    HKDF（RFC 5869）は、HMAC を2段階で使います。

    段階 計算 役割
    抽出（extract） PRK = HMAC(salt, 入力の秘密) 偏りのある秘密から、一様に近い鍵を1つ取り出す
    展開（expand） OKM = HMAC(PRK, info ‖ カウンタ) を必要な長さまで 1つの鍵から、用途ごとに独立した複数の鍵を作る

    info に「client write key」「server write key」のような用途の名前を入れることで、同じ材料から互いに無関係な鍵を作れます。TLS 1.3 の鍵スケジュール（第7回）は、HKDF をこの形で何段も使っています。

    7.3 パスワード: わざと遅くする

    パスワードから鍵を作る（あるいはパスワードを保存する）ときの敵は、データベースを盗んだ攻撃者による「候補を順に試す」攻撃です。パスワードの候補は少ないので、SHA-256 のような速いハッシュでは、GPU で毎秒何十億回も試されてしまいます。

    対策は2つで、どちらも欠かせません。

    1. 塩（salt）: ユーザーごとに違う乱数を混ぜる。同じパスワードのユーザーをまとめて破られることと、事前計算した表（レインボーテーブル）を防ぐ
    2. わざと遅く、重くする: 1回の計算に時間とメモリを使う関数で、攻撃者の1回の試行を高くつかせる
    関数 遅くする仕組み 備考
    PBKDF2 ハッシュを何十万回も繰り返す メモリを使わないので、GPU や専用回路で並列化されやすい
    bcrypt 繰り返し回数（コスト）を指定 入力が 72 バイトまでという制限がある
    scrypt 大きなメモリを使う メモリを使うので、専用回路での高速化が難しい
    Argon2id 時間とメモリの両方を調整できる 2015年のパスワードハッシュ競技の優勝方式（RFC 9106）。新規なら第一候補

    パラメータの目安は、OWASP の Password Storage Cheat Sheet が「Argon2id ならメモリ 19 MiB・反復 2 回・並列度 1 以上」「PBKDF2-HMAC-SHA256 なら 60 万回以上」といった値を示しています。ただし推奨値は計算機の進歩に合わせて更新されるので、採用時には最新版を確認してください。また、自分のサーバで1回のログインにかかる時間（数十〜数百ミリ秒）を測って決めるのが実務の進め方です。

    • 高エントロピーの秘密からは HKDF（抽出してから展開）で用途ごとの鍵を作る
    • パスワードは低エントロピーなので、塩と、わざと遅く重いハッシュ（Argon2id など）で守る
    • 遅くする工夫は攻撃者の手間を定数倍にするだけで、弱いパスワードは守りきれない

    演習問題

    A. 確認

    1. 原像困難性・第二原像困難性・衝突困難性の違いを、攻撃者に与えるものと探すものの違いとして説明せよ。256 ビット出力のとき、それぞれの一般的な攻撃の手間はいくらか
    2. ファイルのダウンロードページに SHA-256 の値が並んで載っている。これは何を守り、何を守らないか
    3. MAC と署名の違いを、「誰がしるしを作れるか」の観点で説明せよ
    4. Encrypt-then-MAC が安全で、MAC-then-Encrypt が危うい理由を、「受信者が最初に何をするか」の違いとして説明せよ
    5. AES-GCM でノンスを再利用したとき、秘匿性と完全性はそれぞれどうなるか

    B. 攻撃と設計

    1. tag = SHA-256(k ‖ m) を使うシステムで、m = "amount=100" のタグから、"amount=100…&amount=9999" のタグを作る手順を説明せよ（パディングの中身も含めて）
    2. パディングオラクル攻撃で、最後のバイトを解くときに「パディングが正しい」と言われる値が2つ見つかることがある。なぜか、どう見分けるか
    3. 1台あたり毎秒 1,000 件を AES-GCM（ランダムな 96 ビットノンス）で暗号化するサーバが 100 台あり、同じ鍵を共有している。NIST の上限 2^32 回に何日で達するか。どう設計し直すか
    4. 新しい Web サービスのパスワード保存方式を設計せよ。関数、パラメータの決め方、塩の扱い、既存の弱い方式からの移行方法を含めること

    C. 実装

    1. SHA-256 の長さ拡張攻撃を実装し、H(k ‖ m) 型の MAC を偽造せよ（Cryptopals Set 4 の問題 29 は SHA-1 版）
    2. CBC のパディングオラクル攻撃を実装し、オラクルだけを使って暗号文を復号せよ（Cryptopals Set 3 の問題 17）
    3. HMAC を標準ライブラリを使わずに実装し、RFC 4231 のテストベクタで確かめよ

    解答と解説

    A. 確認

    1. 原像: 出力 y を与えられ、H(x) = y となる x を探す（2^256）。第二原像: 入力 x を与えられ、同じ出力になる別の x′ を探す（2^256）。衝突: 何も与えられず、同じ出力になる任意の2つを探す（誕生日攻撃で 2^128）
    2. 偶然の破損（ダウンロードの失敗）は検出できる。ただしページ自体が改ざんされれば、ファイルとハッシュ値を両方差し替えられるので、意図的な改ざんは守れない。署名付きのハッシュ値（第6回）が必要
    3. MAC は鍵を共有する全員が作れるので、受信者は「送信者か自分のどちらか」が作ったことしか分からない。署名は秘密鍵を持つ1人だけが作れるので、第三者にも「その人が作った」と示せる
    4. Encrypt-then-MAC の受信者は、最初にタグを検証し、失敗すれば復号しない。MAC-then-Encrypt は最初に復号するので、改ざんされた暗号文に対する復号処理の反応（パディングエラー、処理時間）が漏れる
    5. 秘匿性: 同じ鍵の列が使われ、2つの平文の XOR が漏れる。完全性: GHASH の鍵 H が求まり、任意のメッセージのタグを偽造できるようになる

    B. 攻撃と設計

    1. 鍵の長さ L を推測する。グルー（パディング）= 0x80 ‖ 0x00…0x00 ‖（(L + 10) × 8 を 64 ビットで）で、L + 10 + グルーの長さが 64 の倍数になるようにする。tag を SHA-256 の内部状態として読み込み、処理済みの長さを L + 10 + グルーの長さとして "&amount=9999" を処理すれば、"amount=100" ‖ グルー ‖ "&amount=9999" のタグになる。L は 1〜64 程度を順に試す
    2. 本物の平文の末尾が偶然 0x02 だった場合、偽ブロックで最後のバイトを 0x02 にすると「0x02 0x02」として正しいパディングになる。見分けるには、正しいと言われたあと、最後から2番目のバイトを変えて再度問い合わせる。それでも正しいなら、最後のバイトは 0x01 だった
    3. 合計で毎秒 10^5 件。2^32 ≈ 4.3 × 10^9 なので、約 4.3 × 10^4 秒 ≈ 半日で達する。サーバごと・期間ごとに鍵を分ける（HKDF で導出）、ノンスにサーバ ID と各サーバのカウンタを組み合わせて重複を構造的に防ぐ、AES-GCM-SIV を使う、などで設計し直す
    4. 例: Argon2id、メモリと反復回数は OWASP の最新の推奨値を下限に、ログイン1回が数十〜数百ミリ秒になるよう自社サーバで測定して決める。塩はユーザーごとに 16 バイト以上の乱数を、ハッシュ値と一緒に保存（エンコード済みの文字列に含める）。移行は、次回ログイン時に検証が成功したら新方式で保存し直す。ログインしないユーザーは、古いハッシュ値を新方式でさらに包む（二重ハッシュ）ことで、一括で守る

    C. 実装のポイント

    • 問題10: 先に「自分で全体を計算した SHA-256」と「状態から再開した計算」が一致するかを確かめてから、攻撃に進むと切り分けやすくなります
    • 問題11: 最初のブロックを解くときは、前のブロックとして IV を使います。最後のブロックの平文には、パディングのバイトがそのまま見えます
    • 問題12: 鍵がブロック長（64 バイト）より長い場合は、先にハッシュしてから使う点を忘れやすいです
