    この回で答える問い

    安全な部品をそろえれば、安全な通信ができあがるのか。

    第2回から第6回で、AEAD、DH 鍵交換、署名、証明書、KDF という部品がそろいました。どれも安全性の定義と根拠があります。では、これを組み合わせれば自動的に安全な通信になるのでしょうか。

    答えは「ならない」です。組み合わせ方を誤ると、部品が1つも破れていないのに全体が破れます。正しく組み合わせても、実装が秘密を漏らせばやはり破れます。この回は、組み合わせ（プロトコル）と実装という2つの層で、安全がどう作られ、どう壊れるかを見ます。

    結論を先に言うと、「プロトコルは自作せず TLS 1.3 や Noise のような検証済みのものを使う。暗号の実装は自作せず、誤用しにくい高水準のライブラリを使う。鍵は KMS で管理する」です。この回は、なぜそう言えるのかを中身から理解するための回です。

    到達目標

    • 安全な部品だけで組んだプロトコルが破れる例を1つ説明できる

    §1 組み合わせの罠: 安全な部品だけで破れる

    MAC も乱数も安全なのに、それを使った認証プロトコルが破れることはあるのか。

    1.1 反射攻撃

    アリスとボブが共有鍵 k を持ち、「相手の出した乱数に MAC で答えられたら本物」という相互認証を考えます。MAC は EUF-CMA 安全で、k を知らない人には正しい答えを作れません。ところが下の図のとおり、攻撃者は k を知らないまま認証を通れます。

    攻撃者は MAC を1つも偽造していません。ボブに、ボブ自身の問題を解かせただけです。MAC の安全性の定義（第4回）は「新しいメッセージのタグを作れない」ことで、「正しい相手が、正しい文脈で作ったタグかどうか」までは保証しないのです。

    1.2 プロトコルに求められること

    この例から分かるとおり、プロトコルには部品とは別の要件があります。

    要件 意味 欠けると起きること
    相手の認証 鍵を共有した相手が、本当に意図した相手であること 中間者攻撃（第5回 §2.2）
    文脈の束縛 誰から誰へ、どのセッションの何番目かを、署名や MAC に含める 反射攻撃、別のセッションへの差し込み
    鮮度 古いメッセージの再送を受け付けない リプレイ攻撃
    ダウングレード耐性 弱い方式を選ばせる改ざんを検出できる 古い弱い暗号に落とされる（FREAK、Logjam、2015年）
    前方秘匿性 長期の鍵が将来漏れても、過去の通信は守られる 録画された通信の一括解読（§4）
    KCI 耐性 自分の鍵が漏れても、他人になりすまされて自分が騙されない 鍵の漏洩から被害が広がる

    1つの部品の安全性の定義では、これらは表せません。プロトコルの設計は難しく、長年使われた標準でも欠陥が見つかってきました。ProVerif や Tamarin といった道具で、こうした性質を機械的に検証する研究が進んでいて、TLS 1.3 は設計段階からこの種の形式検証を受けた最初の主要なプロトコルです。

    • 安全な部品だけで組んでも、文脈を束縛しないと反射攻撃で破れる
    • プロトコルには、相手の認証、文脈の束縛、鮮度、ダウングレード耐性、前方秘匿性といった独自の要件がある
    • これらを満たすように設計され、形式検証も受けた実例が TLS 1.3。§2 で中身を見る

    §2 TLS 1.3: 部品の組み合わせ方の手本

    TLS 1.3 は、これまでの部品をどの順番で、何のために使っているのか。

    2.1 ハンドシェイクの流れ

    下の図を1行ずつ進め、各メッセージの説明を読んでください。

    各メッセージを、§1.2 の要件と対応づけると次のようになります。

    メッセージ 使う部品 達成すること
    ClientHello / ServerHello の key_share DH（ECDHE）、耐量子なら ML-KEM も 共有秘密を作る。毎回使い捨てるので前方秘匿性
    Certificate 証明書チェーン（第6回） サーバの公開鍵と名前を結ぶ
    CertificateVerify 署名（第6回） 「この DH の値を送ったのは証明書の持ち主」と示す。中間者攻撃を防ぐ
    Finished HMAC（第4回） ハンドシェイク全体の改ざんを検出。ダウングレードも防ぐ
    アプリのデータ AEAD（第4回） 機密性と完全性

    CertificateVerify と Finished は、どちらもそれまでのやり取り全体のハッシュ（トランスクリプト）に対して計算されます。§1 の反射攻撃が通じないのは、署名や MAC の対象に「このセッションのこれまでの全メッセージ」が入っていて、別のセッションの答えを流用できないからです。

    2.2 TLS 1.2 から何が変わったか

    TLS 1.3（RFC 8446、2018年）は、それまでの攻撃の歴史を踏まえて、選択肢を大胆に減らしました。

    TLS 1.2 まで TLS 1.3
    鍵交換 RSA 鍵輸送、静的 DH、ECDHE など 使い捨ての (EC)DHE と PSK だけ。RSA 鍵輸送は廃止
    暗号化 CBC + MAC（MtE）、RC4、AEAD AEAD だけ（AES-GCM、ChaCha20-Poly1305 など）
    往復回数 2往復 1往復（再接続なら 0 往復も可）
    証明書 平文で送る 暗号化して送る
    鍵の導出 独自の PRF HKDF による鍵スケジュール
    ダウングレード対策 弱い 署名とトランスクリプトで束縛。乱数欄に印を埋め込む

    削られたものの多くは、これまでの回で攻撃を見てきたものです。MtE の CBC はパディングオラクル（第4回 §5）、RSA 鍵輸送は Bleichenbacher 攻撃（第5回 §5.2）と前方秘匿性の欠如（§4）が理由です。

    ClientHello の key_share には、2026 年時点で主要なブラウザと CDN が X25519MLKEM768（X25519 と ML-KEM-768 の組み合わせ）を既定で載せています。従来の DH と耐量子の KEM を両方使い、どちらかが破れなければ安全というハイブリッド方式です。詳しくは第8回で扱います。

    • TLS 1.3 は、DH で鍵を作り、署名で相手を確かめ、HMAC で全体を確認し、AEAD でデータを守る
    • 署名と MAC の対象はトランスクリプト全体。これで文脈が束縛され、反射やダウングレードを防ぐ
    • 攻撃の歴史を踏まえ、RSA 鍵輸送、CBC、RC4 を削った
    • 1つの DH 秘密から、どうやって用途別の鍵を作るのか。§3 で鍵スケジュールを見る

    §3 鍵スケジュール: 1つの秘密から鍵を分ける

    DH で得た1つの共有秘密から、ハンドシェイク用、アプリ用、再接続用の鍵をどう作り分けるのか。どれが漏れると何が読まれるのか。

    TLS 1.3 は、第4回の HKDF を何段も重ねて鍵を作ります。HKDF-Extract で新しい秘密を混ぜ込み、HKDF-Expand で用途ごとに鍵を切り出す、という繰り返しです。下の図で、攻撃者が知っている秘密を選び、どこまで計算できるかを確かめてください（赤が攻撃者に計算できる部分）。

    図から分かることを整理します。

    攻撃者が知っているもの 計算できるもの 意味
    サーバの長期の署名鍵だけ 何もない 署名鍵は鍵の計算に入らない。過去は読めない（前方秘匿性）
    PSK だけ（DH を併用） Early Secret まで 0-RTT の早期データは読まれるが、本体は守られる
    このセッションの DH 秘密 すべて だから DH の秘密は使い終わったらすぐ消す

    鍵を段階ごとに分ける理由は、1つの鍵が漏れたときの被害を、その用途に閉じ込めるためです。ハンドシェイクの鍵とアプリの鍵が別なので、片方の解析結果をもう片方に使えません。各段にトランスクリプトのハッシュを混ぜるので、やり取りが1ビットでも違えば、まったく別の鍵になります。

    • 鍵スケジュールは HKDF の Extract と Expand を重ね、用途ごとに独立した鍵を作る
    • 長期の署名鍵は鍵の計算に入らない。漏れて困るのは、その場限りの DH 秘密
    • 「長期の鍵が漏れても過去は読めない」という性質に名前を付けて、§4 で詳しく見る

    §4 前方秘匿性: 録画された過去を守る

    攻撃者が暗号化された通信をずっと録画していて、何年も後にサーバの秘密鍵を手に入れたら、録画は読めてしまうのか。

    下の図で、鍵交換の方式を切り替えて、6日目に秘密鍵を漏らしてみてください。

    方式 セッション鍵の作り方 長期の鍵が漏れたら
    RSA 鍵輸送 クライアントが作った鍵を、サーバの RSA 公開鍵で暗号化して送る 録画した暗号文を開けば、過去のすべてのセッション鍵が出る
    使い捨ての DH 毎回新しい a, b で g^ab を作り、使ったら消す 長期の鍵は署名にしか使っていないので、過去は読めない

    この「長期の鍵が漏れても、過去のセッションは守られる」性質を前方秘匿性（forward secrecy）と呼びます。2013 年に、大規模な通信の録画と保管が現実に行われていると報じられたことで重視され、TLS 1.3 では必須になりました。耐量子暗号への移行が急がれる理由（今録画して、将来の量子計算機で解く「Harvest Now, Decrypt Later」）も同じ構図です（第8回）。

    4.1 0-RTT の代償

    TLS 1.3 には、以前つないだことのあるサーバに、最初のメッセージからデータを載せる 0-RTT モードがあります。速い代わりに、2つの弱点があります。

    • 早期データは PSK だけで暗号化されるので、PSK が漏れると読まれる（前方秘匿性がない）
    • 攻撃者が早期データを録画してそのまま再送すると、サーバは区別できない（リプレイ）

    そのため、0-RTT で送ってよいのは、何度実行されても結果が変わらない要求（GET による読み取りなど）だけです。「送金する」のような要求を 0-RTT で受け付けてはいけません。

    • 前方秘匿性は、長期の鍵が将来漏れても、録画された過去の通信が守られる性質
    • 使い捨ての DH で得られ、RSA 鍵輸送では得られない。TLS 1.3 では必須
    • 0-RTT は速いが、前方秘匿性とリプレイ耐性を犠牲にする。冪等な要求だけに使う
    • TLS は1回の接続の話だった。何か月も続くメッセンジャーの会話では、§5 のさらに強い性質が欲しくなる

    §5 Signal のダブルラチェット: 盗まれても回復する

    会話が何か月も続くとき、ある時点で端末の中身が盗まれたら、被害をどこまで小さくできるか。

    5.1 2つの性質

    メッセンジャーでは、1つの会話（セッション）が何か月も続きます。途中で端末の中身（鍵の状態）が盗まれることを想定して、2つの方向の性質を求めます。

    性質 守るもの 仕組み
    前方秘匿性 盗まれる前のメッセージ 鍵を一方向の KDF で進め、古い鍵は消す（対称ラチェット）
    侵害後の安全性（PCS） 盗まれた後のメッセージ 返信のたびに新しい DH を混ぜ、攻撃者の知らない秘密で鍵を作り直す（DH ラチェット）

    ラチェットとは、一方向にしか回らない歯車のことです。下の図で、メッセージを送り、途中で鍵を盗ませ、そのあと返信させてみてください。

    5.2 全体の構成

    Signal プロトコルは、次の2段で構成されています。

    1. 初期の鍵合意: 相手がオフラインでも会話を始められるよう、相手があらかじめサーバに置いた公開鍵の束を使って、複数の DH を組み合わせて最初の秘密を作る（X3DH。2023 年からは ML-KEM を加えた PQXDH）
    2. ダブルラチェット: 上の2つのラチェットで、メッセージごとに鍵を進める

    TLS との違いは、PCS まで求めている点です。TLS の接続は短いので、接続ごとに新しい DH をすれば足ります。メッセンジャーは「盗まれたあとも会話が続く」ので、会話の途中で回復する仕組みが要るのです。なお Signal は 2025 年に、ラチェットにも耐量子の KEM を組み込む拡張を発表しています。

    • 対称ラチェットは鍵を一方向に進めて過去を守り（前方秘匿性）、DH ラチェットは新しい秘密を混ぜて未来を回復する（PCS）
    • Signal は X3DH（PQXDH）で会話を始め、ダブルラチェットで続ける
    • ここまでは「設計」の話だった。§6 では、設計が正しくても実装から漏れる話に移る

    §6 実装の攻撃: 正しい方式でも漏れる

    数学的に安全な方式を、仕様どおりに正しく実装すれば、それで安全なのか。

    6.1 タイミング攻撃

    MAC の検証で、受け取ったタグと正しいタグを先頭から1バイトずつ比べ、違ったらすぐ「不一致」を返す実装を考えます。正しく実装された HMAC でも、この比較が秘密を漏らします。一致している部分が長いほど、応答がわずかに遅くなるからです。

    図では、攻撃者は1バイト目の候補 256 通りをそれぞれ何十回も送り、平均の応答時間が一番長いものを正解とみなします。1バイト確定したら次のバイトへ進みます。4 バイトのタグなら総当たりで約 43 億通りのところ、数万回の問い合わせで当たります。「定数時間の比較にする」に切り替えると、時間に差がなくなり、攻撃は外れます。

    # 危ない比較: 違った所で止まる
def verify(tag, expected):
    return tag == expected

# 定数時間の比較: 全バイトを必ず最後まで比べる
import hmac
def verify(tag, expected):
    return hmac.compare_digest(tag, expected)

    ネットワーク越しでは雑音が大きいので難しく見えますが、統計を取れば、インターネット越しで数十マイクロ秒、LAN では 100 ナノ秒程度の差を検出できることが示されています（Crosby ほか 2009）。

    6.2 サイドチャネルの全体像

    タイミングは、サイドチャネル（計算の副産物から秘密が漏れる経路）の一例です。

    経路 何から漏れるか 代表例 対策
    時間 秘密に依存する分岐、早期終了 MAC の比較、RSA の累乗、Lucky Thirteen（2013） 定数時間の実装
    キャッシュ 秘密に依存するメモリの参照先 AES のテーブル参照（Bernstein 2005） テーブルを使わない実装、AES-NI
    電力・電磁波 秘密に依存する消費電力 スマートカードの鍵の抽出 マスキング、ノイズ
    故障の注入 わざと計算を誤らせた結果 RSA-CRT への Bellcore 攻撃 結果の検算
    エラー エラーの種類や有無 パディングオラクル（第4回）、Bleichenbacher（第5回） エラーを区別しない

    6.3 実際の事故

    年 事故 何が起きたか 層
    2008 Debian の OpenSSL 警告を消す修正で乱数の種がプロセス ID だけになり、鍵が約 3 万通りに 乱数
    2014 Heartbleed 長さの確認漏れで、サーバのメモリ（秘密鍵を含む）が読めた メモリ安全性
    2014 Apple の goto fail 行の重複で、署名の検証が飛ばされた 検証の手順
    2017 ROCA 特定のチップの RSA 鍵生成に構造があり、公開鍵から秘密鍵が求まった 鍵生成
    2020 Zerologon AES-CFB8 で IV を全部 0 に固定し、1/256 の確率で認証を通れた 方式の誤用
    2022 Java の ECDSA（Psychic Signatures） r = s = 0 の署名を受理してしまった 検証の手順
    2026 wolfSSL など（AI が発見） 証明書の偽造につながる検証の不備 検証の手順

    最後の行は、AI が暗号ライブラリの実装の不備を自動で見つけた例です（第8回で詳しく扱います）。表を見ると、数学が破れた例は1つもありません。壊れたのはすべて、乱数、メモリ、検証の手順、方式の使い方といった実装と運用の層です。

    • 正しい方式でも、処理時間などの副産物から秘密が漏れる（サイドチャネル）
    • 秘密を扱う比較や分岐は定数時間にする。比較は hmac.compare_digest などの専用関数を使う
    • 現実の事故の大半は、数学ではなく実装と運用の層で起きている
    • では実務ではどう身を守るか。§7 でまとめる

    §7 実務: ライブラリ、鍵管理、チェックリスト

    暗号を専門としない開発チームが、ここまでの落とし穴を避けるには、何をすればよいのか。

    7.1 道具を選ぶ

    一番効く対策は、落とし穴を踏めない道具を選ぶことです。

    水準 例 向いている人
    プロトコル TLS 1.3、Noise、WireGuard、HPKE（RFC 9180） 通信を守りたいすべての人。自作しない
    高水準ライブラリ libsodium、Google Tink、age アプリでデータを暗号化したい人。ノンスや方式の選択を任せられる
    低水準ライブラリ OpenSSL、BoringSSL、Java の JCA、Go の crypto 標準の方式を組み合わせる必要がある人。誤用の余地が大きい
    自作 — 学習目的のみ

    高水準ライブラリは、「AES を CBC で」のような選択肢をそもそも見せません。たとえば Tink では、用途（AEAD、署名など）を選ぶと、安全な方式と鍵の形式がまとめて決まります。

    7.2 鍵管理と封筒暗号

    暗号の強さは鍵の管理で決まります。クラウドの実務では、封筒暗号（エンベロープ暗号）が標準的な形です。

              KMS（HSM の中、外に出ない）
          ┌──────────────┐
          │ 鍵暗号鍵 KEK │
          └──────┬───────┘
                 │ データ鍵を包む／開く（API 呼び出し、記録が残る）
                 ▼
  データ鍵 DEK（データごとに新しく作る）──AEAD──▶ 暗号化したデータ
  保存するもの: 暗号化したデータ ＋ 包んだ DEK
    利点 理由
    鍵がアプリの外に出ない KEK は HSM から出ず、取り出せない
    大きなデータを速く暗号化できる 実際の暗号化はローカルの AEAD で行う
    鍵の更新が軽い KEK を更新しても、包み直すのは小さな DEK だけ
    監査できる KEK の利用はすべて KMS のログに残る
    権限で制御できる 誰がどの KEK を使えるかを IAM で決められる

    これは第5回の KEM/DEM と同じ「鍵だけを重い仕組みで運び、データは速い共通鍵で守る」構造です。

    7.3 レビューのチェックリスト

    項目 確認すること
    方式 AEAD を使っているか。ECB、CBC + MAC の自作、教科書 RSA がないか
    ノンス 同じ鍵で同じノンスを使っていないか。ランダムなら長さは足りるか（第4回 §6）
    乱数 OS の暗号用乱数（/dev/urandom、SecureRandom、secrets）を使っているか
    鍵 ソースコードや設定ファイルに鍵がないか。KMS かシークレット管理を使っているか
    比較 MAC やトークンの比較が定数時間か
    検証 証明書の検証を無効にしていないか。署名を検証してから中身を使っているか
    エラー 復号失敗の理由を外に返していないか
    パスワード Argon2id などで保存しているか（第4回）
    移行 方式を差し替えられる設計か（暗号の俊敏性）。第8回の耐量子移行で効いてくる
    • 自作せず、プロトコルは TLS や Noise、データの暗号化は高水準ライブラリを使う
    • 鍵は KMS で管理し、封筒暗号で使う。鍵はアプリの外に出さない
    • レビューでは、方式、ノンス、乱数、鍵の置き場所、比較、検証、エラーを確かめる

    演習問題

    A. 確認

    1. §1 の反射攻撃を防ぐには、MAC の入力に何を加えればよいか。2つ挙げよ
    2. TLS 1.3 で、CertificateVerify がないと何が起きるか
    3. サーバの署名鍵が漏れた。TLS 1.3 で、(a) 過去の録画、(b) これからの接続、のそれぞれにどんな影響があるか
    4. 0-RTT で「送金」の要求を受け付けてはいけない理由を説明せよ
    5. 前方秘匿性と侵害後の安全性の違いを、「いつのメッセージを守るか」で説明せよ

    B. 攻撃と設計

    1. 1バイトの比較に 20 ナノ秒かかり、測定の雑音が標準偏差 1 マイクロ秒の正規分布とする。1バイトの差を見分けるには、候補ごとに何回くらい測定すればよいか。平均の標準偏差が差の 1/3 程度になる回数で見積もれ
    2. 封筒暗号で、KEK を更新（ローテーション）するとき、既存のデータをすべて暗号化し直す必要はあるか。理由とともに答えよ
    3. あるアプリが、ユーザごとに AES-GCM の鍵を1つ持ち、メッセージごとに 96 ビットのランダムなノンスを使っている。1ユーザが 2^32 通を超えて送ると何が問題か（第4回 §6）

    C. 実装

    1. Wireshark と SSLKEYLOGFILE を使い、TLS 1.3 のハンドシェイクを観察して、図の各メッセージと対応づけよ
    2. X25519、HKDF、ChaCha20-Poly1305 で、相手の公開鍵を事前に知っている前提の小さな暗号化チャネルを組め。メッセージ番号をノンスと関連データに入れること
    3. 非定数時間の HMAC 比較を行うローカルの Web サーバを作り、タイミング攻撃でタグを復元せよ（Cryptopals Set 4 の問題 31〜32）

    解答と解説

    A. 確認

    1. 送信者と受信者の識別子（向き）、セッション識別子やメッセージ番号、これまでのやり取りのハッシュ、など。どれも「その答えが、どの文脈で作られたか」を束縛する
    2. 誰でも自分の DH の値と、本物のサーバの証明書を送れるので、中間者攻撃が成立する。証明書だけでは、公開値を送ったのが証明書の持ち主だと示せない
    3. (a) 署名鍵は鍵の計算に入らないので、過去は読めない（前方秘匿性）。(b) 攻撃者はサーバになりすませるので、中間者攻撃が可能になる。証明書を失効させ、鍵を替える必要がある
    4. 早期データは録画して再送でき、サーバは再送と区別できない（リプレイ）。送金が2回実行される
    5. 前方秘匿性は、鍵が盗まれる前に送られたメッセージを守る。侵害後の安全性は、盗まれたあとに送られるメッセージを、新しい秘密が混ざった時点から守る

    B. 攻撃と設計

    1. 差 20 ns の 1/3 ≈ 6.7 ns を平均の標準偏差にしたい。1000 ns/√N = 6.7 より √N ≈ 150、N ≈ 22,500 回。候補 256 通りなら1バイトあたり約 580 万回。現実的な量で、実際の攻撃はさらに統計の工夫を加える
    2. 必要ない。KEK で包んでいるのは DEK だけなので、DEK を古い KEK で開いて新しい KEK で包み直せば済む。KMS によっては、古い版の KEK を保持して自動で扱う
    3. 96 ビットのランダムなノンスでは、2^32 通あたりでノンスが衝突する確率が約 2^−33 を超え始め、NIST の推奨する上限に達する。ノンスが衝突すると GCM は認証鍵が漏れ、偽造できるようになる。鍵を定期的に替えるか、XChaCha20-Poly1305 のような長いノンスの方式を使う

    C. 実装のポイント

    • 問題9: ブラウザを SSLKEYLOGFILE 環境変数を設定して起動し、Wireshark の TLS の設定でそのファイルを指定します
    • 問題10: 送受信で別の鍵を HKDF で導出し、ノンスはメッセージ番号から作ります。番号の巻き戻りを拒否すればリプレイも防げます
    • 問題11: ローカルでも雑音はあるので、同じ候補を繰り返し測り、中央値を使うと安定します
